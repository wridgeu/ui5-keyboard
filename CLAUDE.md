## Architectural conventions

- **TypeScript-only control authoring.** UI5 controls in `packages/kiosk-keyboard` are written in TS with `.gen.d.ts` interfaces produced by `@ui5/ts-interface-generator`. Never hand-edit `*.gen.d.ts`; run `npm run generate`.
- **Commit the generated interfaces under `packages/kiosk-keyboard/src` (`KioskKeyboard.gen.d.ts`, `CustomLayout.gen.d.ts`); do not gitignore them (#150).** A control uses its `$…Settings` type in constructor overloads without importing it, so the IDE, a bare `tsc --noEmit`, and npm consumers of kiosk's shipped `src/` all read the file before any build runs. Principle: commit a generated file when something reads it before the build; gitignore it when only the build does — that is why webc's `src/generated/` stays gitignored. JSDoc-strip drift (#142/#143/#149) is held by two `verbose` pins (`generate --jsdoc verbose`, `ui5.yaml` `generateTsInterfacesJsDoc: verbose`) plus a CI gate that globs `src/**/*.gen.d.ts`. That gate stages first and diffs `--cached` (`git add -A` then `git diff --cached --exit-code`): a plain `git diff` is blind to a newly generated file that was never committed, which is the case a new control creates.
- **TypeScript pinned to 6.x (`~6.0.3`); do not bump to 7.** `@ui5/ts-interface-generator` is built on the TypeScript compiler API (`ts.factory`, `ts.TypeChecker`, `ts.createWatchProgram`), which the TS7 Go rewrite does not expose, so it caps its peer at `<7.0.0` — and it runs in `prebuild`/`pretypecheck`, so TS7 breaks the whole control-authoring pipeline. It is the only blocker; `@openui5/types` and `moduleResolution: "Bundler"` already work on both. UI5 types come from `@openui5/types`; `@types/openui5` is deprecated and only appears transitively.
- **UI5 string enums live in `library.ts`.** Declare as `export enum X { Foo = "Foo", ... }` directly in `library.ts` (the shape `@ui5/ts-interface-generator` emits, which imports them by name from the library module). Register each with `DataType.registerEnum("fully.qualified.Name", X)` and list the qualified names in `Lib.init({ apiVersion: 2, types: [...] })`. Do not attach them to the library namespace via `ObjectPath`/`thisLib.X = X`: under `apiVersion: 2`, XML `core:require` binds to the module's named exports and runtime type validation resolves through the `DataType` registry. Compare with string literals (`=== "Foo"`), since TS string enum members are string literals at runtime. Do not split enums into per-file modules — UI5 treats those as pseudo-modules and resolves them to `undefined`. Numeric enums differ: `DataType.createType` extending `int`, TS `enum`, type-only import.

  Exception: **an enum that is also the component type of an array property uses `DataType.createType` over the `string` base** (`ui5.kiosk.LayoutFacet`, for `suppress`; #223). UI5's array parser splits on commas without trimming, and a registered enum maps any unknown token to `undefined`, so under `registerEnum` the space in `suppress="Variants, Middleware"` is indistinguishable from a misspelling and rejects the whole view. `createType` supplies a `parseValue` that trims the token and an `isValid` that checks enum membership, so conforming markup parses and a real typo still fails loudly. Pass `defaultValue`, or the type inherits the `string` base's `""` — a value its own `isValid` rejects. The `export enum` and the `Lib.init({ types })` entry are unchanged; scalar enum properties (`layoutRole`, `keyboardType`) keep `registerEnum`. Trade-offs: `docs/specs/2026-08-05-token-list-attributes-design.md` §4.1.

- **No shared-core package across `kiosk-keyboard` and `kiosk-keyboard-webc` (declined in #105).** The two keep parallel copies of the framework-agnostic logic (`grapheme`, `auto-repeat`, `shift-state`, `composition-utils`, `key-token`, plus the diverged `layout-registry` / `input-operations` / `middleware-registry` / i18n / detector). The dominant constraint if ever revisited: kiosk ships UI5 AMD resolved by namespace, so it cannot carry a runtime npm dependency — any shared core must be vendored into `ui5/kiosk/*` at build time, never depended upon. webc is bundler-consumed and would inline one trivially; that asymmetry is why the usual "publish a core, depend on it" pattern does not transfer. Drift is the accepted tax (#98, #108); if it bites again, prefer a CI divergence check over extraction. Full analysis in #105.

## UI5 framework notes (project-specific)

- **Modules load once and never unload.** SAPUI5 caches factory results for the page lifetime. In a launchpad, switching apps destroys the component but leaves module-level state intact — a `let cache = null` at factory scope survives across app restarts. Keep state on component- or control-scoped instances, never module closures.
- **`sap.ui.core.IAsyncContentCreation` on every Component owning views.** Flips `rootView`, router, and nested views to async, and rejects `Component.create` on broken view definitions instead of degrading silently. Caveat: nested components loaded via `ComponentContainer` are still not async by default.
- **Lifecycle hooks must not return a value.** Since 1.120, returning anything (including a Promise from `async onInit`) logs an error and is scheduled to fail. Keep hooks synchronous; fire-and-forget async work from inside.
- **Clean up globals in exit.** `EventBus`, `Theming.attachApplied` (`sap/ui/core/Theming`, since 1.118) and `Localization.attachChange` (`sap/base/i18n/Localization`, since 1.120) are page-level. Every `subscribe`/`attach*` needs a matching `unsubscribe`/`detach*` in `exit`/`destroy`, or the callback fires against a torn-down context.
- **Prime the static-area live region from `onBeforeRendering`, not `init`.** `sap.ui.core.InvisibleMessage` is a lazy singleton whose `getInstance()` is what inserts its `role="status"` spans. Priming is not functionally required — it buys the ARIA property the class documents: a live region should be in the page and empty before the write, because create-and-write in one task is what screen readers drop. `onBeforeRendering` is self-gating: `Control.prototype.placeAt` wraps its whole body in `Core.ready`, so the static area resolves there. From `init` it would need its own `Core.ready`, since `init` runs wherever something says `new` and `StaticArea.getDomRef` throws while the document is still parsing. Every `sap.m` control that primes does so from a rendering hook; none primes from `init`. Not observable from a test — the singleton is module-global and never reset, so any earlier `getInstance()` primes it for the rest of the page. This repo: `KioskKeyboard.onBeforeRendering`; evidence and the framework survey in `docs/specs/2026-08-26-live-region-exposure-adversarial-hypotheses.md`.
- **Detach DOM listeners with an `AbortSignal`, not a stored bound reference.** Arm `addEventListener(type, handler, { signal })` for an armed period and end it with one `abort()`, so teardown cannot half-happen and handlers can be inline arrows. Two hazards this trades for: a signal is **one-shot**, so every re-arm must mint a fresh controller (derive any `isActive()`-style flag from `_abort !== null` so it cannot read true against a reused aborted one); and inline arrows lose `addEventListener`'s dedupe of identical `(type, listener, capture)` triples, so an arm path that can run twice without an intervening abort must abort first (`KioskKeyboard.ontouchstart`). Ship a re-arm regression test — disable, enable, assert the listener still fires — because a suite that only asserts teardown passes against a reused aborted controller. Canon: `AutoShowBehavior.enable/disable`, `KioskKeyboard.show/close/exit`, `VariantPopupBehavior`, webc's `AutoShowController.sync`.
- **The renderer is `apiVersion: 4`; do not let a linter or modernization skill "fix" it to 2.** Every `ui5-modernization` rule and most guidance says "add `apiVersion: 2` to renderer objects" — here that is a downgrade. 4 is a strict superset (it requires all of 2, plus rendering encapsulation) and lets `RenderManager` skip re-rendering the control when only a parent property changed. What it costs: the renderer must render only the control's own properties, aggregations and associations, never parent or external state; a parent whose state a child's output depends on must `invalidate()` the child. The skip additionally needs every descendant renderer at 4 and no `addEventDelegate`-registered `onBeforeRendering`/`onAfterRendering` without `canSkipRendering: true` — a control's _own_ hook is not a delegate and does not forfeit it.
- **Declarative XML before workarounds.** When a control exposes a property/aggregation/event for the intent, use it rather than controller logic, renderer subclassing, or override CSS. DOM manipulation and override CSS are footguns: lost on re-render, accessibility regressions, theme drift.
- **Bind, don't manipulate.** Prefer property/expression bindings and formatters over `setVisible`/`setEnabled`/`setText`. With one-way bindings, imperative writes are reverted on the next refresh; with two-way, they silently propagate into the model. Hoist repeated compound expressions into a `viewState` JSON-model flag. Formatters are one-way and run with undefined inputs, so every parameter must tolerate `undefined`/`null`.
- **Close dialogs via the dialog's close event.** `sap.m.Dialog` also closes via ESC and via the router (`closeOnNavigation`, since 1.72), not only buttons. Hang result propagation and cleanup off the close event.
- **`sap.ui.define` exports; `sap.ui.require` does not.** Use `define` for any file another module imports; `require` for one-shot deferred imports inside event handlers.
- **Keycaps are `<div role="button">` in both packages, not native `<button>`; do not "modernize" them.** The role exposes the same node to assistive tech as the native element, and Enter/Space activation already comes from UI5's `sapselect` pseudo-event, which the framework filters to Enter/Space with no Ctrl/Alt/Shift/Meta held — stricter than a native button. The Shift half is re-admitted deliberately through `sapselectmodifiers` as "type the shifted glyph", leaving Ctrl/Alt/Meta unhandled; both handlers share `_activateFocusedKey`. Switching would cost a UA reset for `appearance`/`font`/`padding`/`border`/`background`/`color` in a stylesheet that today carries no hardcoded colors and no `!important`; a `type="button"` on every key or an enclosing form submits; and a second activation path, since a native button's Enter/Space fires `click` while pointer activation runs through `ontouchend`, whose surface-wide `preventDefault()` (which keeps focus on the target input) also kills the click chain. `disabled` is wrong here too — it drops a key out of the tab order and breaks the roving tabindex, which is why the renderer writes `aria-disabled` plus `tabindex="-1"`. Windows High Contrast comes from the explicit `forced-colors: active` block, not a UA button default.
- **Give a control's own persistent sub-controls a stable id derived from `getId()`.** Id them as ``new SubControl(`${this.getId()}-suffix`, { ... })`` the way core controls id their internals (`sap.m.DatePicker`'s calendar is `getId() + "-cal"`; `sap.m.Select` ids its `-labelIcon`, `-valueStateText`, `-message` and `-hiddenInput` internals this way), rather than letting UI5 auto-generate a volatile `__controlN`. The convention is not universal in `sap.m` — `Select`'s own list and `ComboBoxBase`'s picker take auto-ids — so treat it as the house rule it is, not as something every core control models. The derived id is deterministic, collision-free, namespaced, and stable across opens for ARIA references and tests. Applies to persistent owned controls; genuinely transient per-render children may keep auto-ids. This repo: `KioskKeyboard._getVariantPopover()` → `${this.getId()}-variantPopover`.
- **A control that owns exactly one internal popup holds it in a named, typed, hidden 0..1 aggregation**, not a per-open `new` + `dependents`/`addDependent` bridge. Declare `_name: { type: "sap.m.Popover", multiple: false, visibility: "hidden" }` in `metadata.aggregations`: hidden keeps it out of the settings interface, `applySettings`, XML and cloning, and the generator emits no public accessors, so touch it only via generic `getAggregation`/`setAggregation(name, popover, true)`. Create the shell once lazily and reuse it across opens; rebuild its content each open (`destroyContent()` / `removeAllAriaLabelledBy()`, then re-add); dismiss with `close()`, never `destroy()`. No manual teardown in `exit` — `ManagedObject.destroy` runs `exit` first, then the aggregation-destroy loop. Neither aggregation carries DOM content-density into the static area, so mirror it per open with `sap/ui/core/syncStyleClass`. Canon: `sap.m.DatePicker._popup` (`sap.m.ResponsivePopover`), `sap.m.Menu._dialog` and `._menu`, `ComboBoxBase`'s `picker`; this repo: `KioskKeyboard._variantPopover` (#162).

## 1. Before coding

- State assumptions explicitly. If multiple interpretations exist, surface them; don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- Every changed line must trace to the user's request. Don't "improve" adjacent code, comments, or formatting; match existing style even if you'd do it differently.
- Comments and doc-blocks describe the current contract, not the edit that produced it. No refactor narration ("now a discriminated union", "collapsed from two fields", "renamed from X"), no before/after history, no justifying the diff in prose. That belongs in the commit message or PR. A reader a year out wants what the code does, not how it got there.
- When your changes orphan imports/vars/functions, remove them. Don't delete pre-existing dead code unless asked.

## 2. Sharing has a cost

Before extracting a helper, weigh the shared code against: a new file, a new import edge, a new internal API to keep stable.

Hoist when the shared code is non-trivial (several lines, not a regex/ternary), when the duplicates risk diverging incorrectly (different test coverage or bug fixes), or when a third call site appears. Otherwise duplicate. Never add "keep byte-identical" comments: if the duplication is small enough that you considered hoisting and chose not to, no comment is needed.

## 3. Bug fixes ship with regression tests

Write the failing test first. If you can't reproduce the bug in a test, you don't understand it well enough to fix it.

- Helper / pure-logic bugs: unit test in the corresponding `.qunit.ts` (kiosk) or `.test.ts` (webc, vitest).
- Integration bugs: control-level QUnit test using the internals cast pattern.
- Untestable bugs (e.g. framework rendering timing): state that explicitly and include manual repro steps.

## 4. No test-only code in production modules

Production modules must not export functions whose only callers are tests (`_resetCache`, `hasResolver`, `_getInternalState`). The production code never needs them and they leak internals into the public surface. Instead:

- Observe behavior through the public API (assert that `getText()` returns base text after a clear, rather than peeking at a `hasResolver()` flag).
- Use sinon to stub/spy collaborators at module boundaries.
- Put genuine test scaffolding in `test/helpers/` and import it only from tests.

If a test seems to require a production-side helper, it is probably asserting on internal state instead of behavior; rewrite the assertion.

## 5. Code review methodology

- No scoring or confidence ranking. A finding is real or it isn't.
- Verify each finding against the actual code and CLAUDE.md / UI5 API docs / existing patterns. Discard anything that doesn't survive that check.
- Report surviving findings in the current conversation. Do not post to GitHub unless explicitly asked.

## 6. UI5 framework lookups

Verify UI5 APIs against the pinned version (see each package's `ui5.yaml` / `package.json`). Version numbers and `since` markers across these sources are out of sync, so cross-check rather than trusting the first hit. Many `sap.ui.getCore()` accessors were deprecated across 1.118–1.120 in favor of `Theming`, `Localization`, `Messaging`, `Element`, `Lib`. Source order:

1. **Local cache** `~/.ui5/framework/packages/@openui5/...`: authoritative for the installed version. Grep here first.
2. **`SAP/openui5` GitHub**: when the local cache lacks the version. Cite commit-pinned URLs.
3. **OpenUI5 SDK API reference** and the `ui5-mcp` tool (`get_api_reference`): for high-level contracts and `since` markers.

## 7. Adversarial test validation

A green suite can lie: a test asserts nothing, the runner reports success while executing zero tests, or a tolerance or skip hides the regression. Before trusting a suite — especially after a test-infrastructure change — prove it fails on real breakage instead of only watching it pass.

- Write the false-positive hypotheses down first (how could a green run be lying?) in a dated `docs/specs/*-adversarial-hypotheses.md`.
- Clear each hypothesis only after you have SEEN the suite go red for it, then revert: flip one assertion (is it live?), corrupt one committed baseline (does the visual test compare?), inject one failing assertion (does the exit code propagate?), point the runner at a bogus path (does it pass empty?).
- Code review and agent audits are corroboration, not proof. Confirm empirically.
- Watch for: vacuous assertions, skips that fire on all targets, snapshot tolerances large enough to mask a one-element change, and runners that pass while running zero tests.
- **CI compares no pixels, so a visual spec is not coverage there.** `test:e2e:ci` passes `--ignore-snapshots`, and so does `check` (via `test:e2e:no-pixels`); both `playwright.config.ts` files additionally narrow the device projects to `invariants.spec.ts` under `CI`. The committed baselines are therefore compared only by a deliberate `npm run visual:check`, on the OS that wrote them (Windows; the filenames carry no platform suffix), and nowhere else. When a visual spec is the only home for a behaviour, give it an assertion that runs without pixels (#281). In webc the narrowing also drops the two `(pointer: coarse)`-gated cases in `visual.spec.ts` entirely — the desktop project skips them — so those run nowhere on CI. Locally the pixels do not close the gap either wherever a snapshot takes the `SOFT` tolerance, which absorbs a baseline miss an order of magnitude above a one-keycap change (`visual.spec.ts`).

## 8. Every assertion must be able to fail

**Hard rule: before writing or accepting an assertion, name the concrete change to production source that would make it fail. If no such change exists, it is not a test.** Delete it, or replace it with one that can. An assertion that holds for every implementation costs the same to run as a real one and buys a false sense of coverage, which is worse than an acknowledged gap (#268 is exactly that: a tautological test that looked like coverage for two `isConnected` guards nothing else touched).

The check is per assertion, not per test. A test can carry three real assertions and one that cannot fail.

**Shapes that have actually shipped here. Recognise them on sight:**

1. **A negative an absence satisfies.** `expect(readDataKeys(el)).to.not.deep.equal(CUSTOM)` passed when nothing rendered at all, because the helper returns `[]`. Pin the positive: `to.include("q")`. Same for any `notOk`/`not.toContain` where an empty or missing value clears the bar.
2. **Excluding a value production cannot produce.** `expect(getRegisteredLayoutNames()).not.toContain("instance-only")` where the getter takes no instance map and the name was registered nowhere — `not.toContain("banana")`.
3. **An unreachable precondition.** `setDocked(true) resets open state` where `show()` returns early unless docked, so `_open` was never true. The state being "reset" was never entered.
4. **A value the test or a helper authored end to end.** `assert.ok(getRequiredKeyElement(...))` when that helper throws on a miss; `classList.contains(classes.key)` when the selector is already `.ui5KioskKey[tabindex="0"]`.
5. **An expected value that equals the fallback.** Asserting a locale resolves to `"qwerty"` when `DEFAULT_LAYOUT` is `"qwerty"`: a lookup matching nothing gives the same answer. Point the fixture at a non-default name.
6. **The wrong key, target or instance.** Registering `F10` and firing `F3`; asserting on a freshly built manager instead of the destroyed one. The assertion is about something production never reached.
7. **Both sides derived from one source.** `toHaveLength(C(NAV_KEYS.length, 2))` where the loop and the expectation both read `navRow` — true for any row size, including an empty one. Pin the literal.

**These are NOT tautological. Do not "fix" them:** `assert.ok(true, "did not throw")` as a sole assertion (QUnit fails the test if the call throws, and converts an uncaught throw inside a listener into a failure too); `assert.ok(true)` paired with `assert.expect(N)`; a round-trip used as a precondition guard immediately before a real assertion; identity assertions against a shared frozen constant, which pin that no copy was allocated; golden-literal pins; existence checks on a lookup that can return `undefined`.

**Proof obligation.** When you fix one of these, break the production line it now guards, watch that test go red, revert, watch it go green — and say so in the commit. Reasoning is not enough: two fixes in the #265 sweep were themselves unfalsifiable and only injection caught it (a spy that re-set an unchanged association never reached the flag, because `ManagedObject.setAssociation` early-returns on an unchanged id). Where a claim genuinely cannot be observed from a test, say so explicitly instead of writing a test that passes for the wrong reason.
