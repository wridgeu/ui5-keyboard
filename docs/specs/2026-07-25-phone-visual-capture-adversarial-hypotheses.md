# Adversarial hypotheses: phone visual-capture fix (#204)

Date: 2026-07-25

On the three phone projects, `expect(locator).toHaveScreenshot()` cropped the wrong page region: 24-31 of ~50 baselines per profile showed a different fixture than the one under test. `desktop` and `tablet` were correct.

Root cause is the fixture page's horizontal overflow. Fixtures are pinned to 320/400/600px (`#kb-wide` is the widest), so the document is 620px wide whatever the viewport, and an element screenshot then breaks in two independent ways:

- **LTR.** With `isMobile: true` Chrome honours the page's `width=device-width` meta and inflates the layout viewport to the overflowing content width, reporting `620x1101` against an emulated `320x568`. `scrollIntoViewIfNeeded` scrolls into that inflated viewport while the capture stays visual-viewport sized, so the crop misses. Measured directly: after scrolling `kb-numeric` into view at phone-sm, `getBoundingClientRect().y` is 698.8 while `documentElement.clientHeight` is 568.
- **RTL.** The scrollable overflow grows leftwards and `scrollX` is measured from the right edge, so the viewport-relative box maps to a document offset 300px off. Independent of `isMobile`.

Fix: `expectVisualMatch()` crops a full-page capture to the element's document box, correcting for the RTL overflow direction. Full-page captures are already in document coordinates, the same space the clip is measured in.

A test-infrastructure change like this can go green for the wrong reason. Each hypothesis was cleared only after the suite was **seen** to fail for it, or after the claim was measured directly.

## Deliberate exceptions

- **`kb-docked` keeps an element screenshot.** It is `position: fixed`, so it has no document box: a full-page capture pins it to the resized viewport. The case is skipped on all three phone projects (`docked render unstable under phone emulation`) and so only runs on desktop and tablet, where the element path is correct.
- **Three tablet baselines changed.** `tablet/kb-qwerty-nav` is the #205 icon-bump fix. `tablet/kb-numpad` and `tablet/kb-numpad-rtl` shift by a single row: the numpad's bottom edge is fractional, and cropping an enclosing integer box from a full-page capture includes a sliver of what lies below the element, where an element screenshot clips to the element. Verified by diffing expected against actual: 296 differing pixels, every one of them on the last row (`y=330` of 331), max channel delta 77. Inherent to the mechanism, not a content change.

## Rejected alternative

Dropping `isMobile: true` from the device profiles also fixes the LTR case, is layout-neutral (`clientWidth` stays at the emulated width, `(pointer: coarse)` / `(hover: none)` / `maxTouchPoints` unchanged, key geometry identical to measurements taken under real mobile emulation), and needs no spec changes. It was rejected because it does not fix RTL: H7's blank baselines were produced under that variant. It also drops meta-viewport handling, which is part of what makes a phone profile a phone.
